# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Kharchify is a personal expense tracker (INR): log expenses by category, set daily/monthly budgets, see where money goes. Used on laptop and iPhone, so all data lives on the backend. Agreed design, decisions and roadmap: @docs/ARCHITECTURE.md

## Layout
- `backend/` — FastAPI + SQLAlchemy 2.0 + Alembic. SQLite in dev, PostgreSQL planned for deployment.
- `frontend/` — not built yet. Planned: Next.js (App Router) + TypeScript, Tailwind, Recharts, installable as a PWA (no separate native app). Next.js is UI only: all data goes through the FastAPI API — no Next.js API routes or direct DB access.
- `docs/iphone-shortcut.md` — user guide for the iPhone Shortcut that calls `GET /categories` and `POST /expenses` with an API token. Keep it in sync if those endpoints' request/response shapes change.

## Deployment
- Backend on Vercel (serverless FastAPI, project root `backend/`, entrypoint `app/main.py`, region `sin1`, config `backend/vercel.json`); database Neon PostgreSQL via Vercel Storage. Steps in `docs/DEPLOY.md`.
- Every push to `main` redeploys. Production builds run `backend/scripts/vercel_build.py` → `alembic upgrade head` (using `DATABASE_URL_UNPOOLED`), so a broken migration fails the deploy. Preview builds skip migrations but share the DB.
- Serverless: no long-running process, no background threads/schedulers, read-only filesystem (no SQLite in prod). Anything periodic must run on request.
- Vercel runs Python 3.12+; the venv is 3.13 (`backend/.python-version`). Don't use 3.11-only or 3.14-only features.
- `DATABASE_URL` from hosts (`postgres://…`) is rewritten to `postgresql+psycopg://…` in `app/config.py`.
- `ALLOW_REGISTRATION=false` in production after the owner's account exists.

## Environment rules (strict)
- **Never install anything globally.** Python packages go only into `backend/.venv`; always invoke tools through it: `.venv/Scripts/python -m pip|pytest|alembic|uvicorn ...` (Windows venv layout — `Scripts/`, not `bin/`). Don't rely on an activated shell.
- Frontend: local `npm install` only — no `npm install -g`, no globally installed CLIs.
- Runtime deps go in `backend/requirements.txt` (deployed); test-only deps in `backend/requirements-dev.txt`. Install locally with `-r requirements-dev.txt`.

## Commands (run from `backend/`)
- Dev server: `.venv/Scripts/python -m uvicorn app.main:app --reload` → API docs at http://localhost:8000/docs
- Tests: `.venv/Scripts/python -m pytest -q` (single: `-k test_name`)
- New migration after changing `app/models.py`: `.venv/Scripts/python -m alembic revision --autogenerate -m "msg"`, review the file, then `.venv/Scripts/python -m alembic upgrade head`; `alembic check` confirms models and migrations match.

## Conventions
- Layers: `routers/` only handle HTTP; logic lives in `services/` and raises `app/errors.py` errors (`NotFoundError`, `ConflictError`, `BadRequestError`), which `main.py` turns into `{"detail": ...}` responses. Don't raise `HTTPException` from services.
- Money: `Numeric(12, 2)` columns and `Decimal` in Python — never `float`. Format for users with `format_inr` (Indian digit grouping).
- "Today" is the user's local date: use `today_for(user)` (`users.timezone`, default `Asia/Kolkata`), never `date.today()`.
- Every query on user data must be scoped to the current user; another user's IDs return 404, never 403.
- Auth: `CurrentUser` accepts a login JWT or a personal API token (`kh_…`, stored as SHA-256). `SessionUser` is JWT-only — use it for anything an API token must not do (token management).
- Categories are archived (`is_archived`), not deleted; archived ones can't receive new expenses.
- Schema changes only via Alembic migrations; the app never calls `create_all` (tests do, on in-memory SQLite — see `tests/conftest.py`). Constraint names come from the naming convention in `app/database.py`.
- Migrations must work on PostgreSQL too: check autogenerated `server_default`s (booleans need `sa.false()`/`sa.true()`, not `'0'`).
- `expenses.category_id` FK is deliberately NO ACTION (not RESTRICT) so deleting a user cascades; tests cover this.
- Config comes from `app/config.py` (pydantic-settings, reads `backend/.env`); see `backend/.env.example`. Alembic reads the DB URL from there too, not `alembic.ini`.
- `POST /auth/login` is an OAuth2 form: the email goes in the `username` field.

## Gotchas
- The repo is inside OneDrive; files (e.g. `kharchify.db`) can be locked while syncing, so deletes may fail with "resource busy".
- `.venv/Scripts/python.exe` is a launcher that spawns the real interpreter as a child, so `kill $!` leaves the server running. Stop a test server by the PID listening on its port (check its command line first) — never kill all `python.exe`/`node.exe`.
- Use `set -o pipefail` when piping commands through `tail`/`grep` in `&&` chains, or failures are hidden.
